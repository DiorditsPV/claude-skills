# skill-new

Создаёт новый скилл по нашему канону. Главная цель — **компактность**: по
умолчанию ОДИН `SKILL.md`, без папок «на вырост».

## Шаг 1. Наводящие вопросы (brainstorming-first — ОБЯЗАТЕЛЬНО)
До создания любых файлов задай пользователю **3–5 наводящих вопросов** и дождись
ответов — не приступай к скиллу, пока замысел не прояснён. Если развилок
несколько, спрашивай одним блоком (AskUserQuestion). Покрой:
1. **Боль/сценарий** — какую повторяющуюся задачу фиксируем? (реальный случай, не «на всякий случай»)
2. **Триггеры** — какими словами/фразами пользователь позовёт скилл?
3. **Границы** — это одна способность? чем отличается от соседних скиллов?
4. **Тип шагов** — детерминированные (→ скрипт) или суждение (→ проза)?
5. **Выход** — что скилл выдаёт на выходе? нужен ли шаблон артефакта?

Адаптируй число к задаче (3–5): не спрашивай то, что уже однозначно задано.

## Шаг 2. Имя
lowercase-with-hyphens, ≤64, ясная способность (не `helper`/`utils`). Проверь
отсутствие пересечений: `ls ~/.claude/skills`.

Рабочий (проектный) скилл именуется `<домен>-<алиас>`: префикс домена плюс короткий алиас
действия в одно-два слова — `rvi-task`, `rvi-release`, `rvi-to-wiki`, `rvi-kb-update`. Внутри
алиаса не повторяй домен и не тащи служебные хвосты `-agent`, `-docs`, `-skill`. Личные
кросс-проектные скиллы остаются без префикса: по имени сразу виден периметр.

## Шаг 3. description (самое важное — только он висит в контексте)
- 3-е лицо, «Use when…» / «Используй, когда…»;
- **WHAT + WHEN** в одной фразе;
- дискриминирующие ключевые слова (слова запроса пользователя);
- ≤1024 символа;
- если рядом есть похожий скилл — фраза-граница «в отличие от …».

## Шаг 4. Тело SKILL.md
< ~500 строк, читается за один проход. Структура: краткая цель → когда
применять → пошаговый процесс → (опц.) анти-паттерны / формат выхода.
**Линкуй, не дублируй.**

## Шаг 5. Доп. файлы — только если оправдано
Заводи файл ТОЛЬКО при одном из условий:
- переиспользуется в нескольких контекстах;
- крупный редкий справочник (>~100 строк) → `reference/`;
- исполняемый скрипт (его запускают, а не читают) → `scripts/`;
- каркас выходного артефакта → `templates/`.

Иначе всё держи в `SKILL.md`. Пустые папки не создавай.

## Шаг 6. Куда положить
- Личные кросс-проектные → `~/dev/claude-skills/skills/<name>/`, затем симлинк
  `~/.claude/skills/<name>`. Репозиторий публичный, код живёт на ветке `main` и
  мержится в `data` — заводи скилл на `main`, иначе он застрянет.
- Рабочие/проектные → в KB репозитория проекта (`<repo>/.claude/<kb>/skills/<name>/`);
  симлинки в `<repo>/.claude/skills` раскладывает bootstrap-скрипт KB.

Граница простая: если в скилле есть рабочая специфика — внутренние хосты, имена
каталогов и витрин, номера задач — он проектный, в публичный репозиторий не идёт.
При коллизии имён персональная копия (`~/.claude/skills`) выигрывает у проектной.

Создай `<name>/SKILL.md`.

## Шаг 7. Самопроверка
Прогони новый скилл через режим проверки ниже прежде чем считать готовым.

## Режим проверки (аудит написанного скилла)

Тот же канон, но применённый к существующему скиллу — своему только что созданному
или чужому. Вход: путь к директории с `SKILL.md` (или несколько; не задан — спроси либо
просканируй `~/.claude/skills`, учитывая симлинки). Файлы не меняй без явной просьбы.

1. Факты: длины файлов (`find "$DIR" -type f | sort`, `wc -l`), frontmatter, объём
   `description` в символах.
2. Описание — по критериям шага 3; имя — по шагу 2.
3. Компактность — по критериям шагов 4 и 5.
4. Анти-паттерны, флагуй явно: размытое `description` без WHEN и триггеров; преждевременное
   дробление (50-строчный скилл на шесть файлов); дублирование тело ↔ `reference/*`;
   гигантские блоки кода в теле вместо ссылки на скрипт; пустые папки.

Выход по каждому скиллу: **вердикт** (эталон / доработать / переписать) → найденные
проблемы → конкретная правка, вплоть до переписанного текста `description`.

## Шаблон SKILL.md
```markdown
---
name: <kebab-name>
description: >-
  Используй, когда <WHAT> … <WHEN/триггеры>. … В отличие от <сосед> — … .
---

# <kebab-name>

<одна строка: что делает и когда>

## Когда применять
- …

## Процесс
1. …

## Выход
- …
```
